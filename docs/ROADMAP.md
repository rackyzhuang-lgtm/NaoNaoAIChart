# 开发路线图

路线图按验收门槛推进。未满足前一阶段门槛，不并行扩大到支付、Passkey 等高风险模块。

## 阶段 0：初始化与决策

状态：进行中。

已完成：

- 盘点空仓库、Git 状态和本地远程配置。
- 基于 2026-08-05 上游 SHA 分析 Chatbox 与 sub2api。
- 建立项目、架构、路线图、状态、上游、决策和任务记录体系。
- 提出控制面/数据面分离的集成方案。
- 已确认以 Chatbox 为代码基线，并通过 HTTP API 对接已部署的 sub2api。

退出条件：

- 确认首发实例策略、登录方式和首发普通用户功能。
- 确认 Chatbox Git 历史导入方式和目标默认分支。

## 阶段 1：基线与技术验证

目标：先证明“可安全登录、可管理 Key、可完成真实模型调用”。

计划：

1. 导入并锁定 Chatbox 基线，建立 `upstream-chatbox` 同步方式。
2. 在未改业务前完成依赖安装、类型检查、单测和桌面启动冒烟。
3. 针对已部署实例建立 sub2api API contract fixture；至少覆盖公共设置、登录、刷新、当前用户、Key CRUD、模型列表。
4. 实现可配置服务地址、HTTPS/URL 校验和连接测试。
5. 验证主进程 token 存储与 refresh 单飞策略。
6. 用自建 Provider 完成协议探针，再决定首发是否立即新增内置 `sub2api` Provider。
7. 完成登录 -> 创建/选择 API Key -> `/v1/models` -> 流式对话的端到端闭环。

退出条件：

- 三个桌面平台至少有明确构建矩阵，Windows 开发环境先通过。
- 令牌不暴露给不必要的 renderer 接口。
- Key CRUD 与模型调用有自动化测试和手工冒烟记录。
- 上游原有 Chatbox 核心测试无新增回归。

## 阶段 2：普通用户 MVP

目标：覆盖最高频自助操作。

- 账户概览、余额/配额、订阅摘要。
- API Key 完整管理和默认 Key 切换。
- 用量统计、趋势、模型维度和错误请求详情。
- 可用渠道、模型广场、公告。
- 兑换码。
- 会话过期、断网、限流和服务端功能关闭的恢复体验。

退出条件：主要流程不再需要打开 Web 控制台；所有页面遵守普通用户权限。

## 阶段 3：账户、安全与支付

- 个人资料、修改密码、通知邮箱和账户绑定。
- TOTP、Passkey 和已确认需要的 OAuth 登录方式。
- 套餐、订单、支付发起、状态轮询、取消和退款申请。
- 外部浏览器/二维码回调后的桌面恢复流程。
- 推广返利和转余额：待确认是否纳入。

退出条件：安全威胁模型和支付异常矩阵完成；关键路径有端到端测试。

## 阶段 4：扩展能力

- 批量图片任务、下载和任务历史。
- 用户可见渠道监控。
- 多实例与多账号切换：待确认。
- Web 构建：待确认。

## 阶段 5：发布与长期维护

- Windows、macOS、Linux 安装包和升级策略。
- 代码签名、公证、更新通道和回滚演练。
- GPL/LGPL 许可证、源代码和第三方声明审查。
- 定期同步 Chatbox 与 sub2api API 变化。
- 建立兼容性矩阵、遥测/崩溃上报策略和发布清单。

## 第一阶段建议节奏

不承诺具体日历工期；在确认范围后按以下可验收批次推进：

1. 基线导入与绿色构建。
2. API contract 与安全登录 spike。
3. Key 管理和 Provider 自动配置。
4. 真实流式对话 E2E。
5. 主 Agent 集成审核、安全复核和阶段验收。
